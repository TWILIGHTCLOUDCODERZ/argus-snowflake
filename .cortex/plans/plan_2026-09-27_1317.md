## Context

**Database state (the duplication problem):**
- TYP-0003 has 12 VERIFIED findings (should be 1); TYP-0001/0002/0005 each have 2; TYP-0004 has 3
- 68 filings total (63 DRAFT_PENDING_HUMAN + 5 REJECTED_GROUNDING)
- 3 ADHOC findings (all REJECTED)
- Every filing path call creates new findings + new filings unconditionally

**Root causes in `app/orchestrator.py`:**
1. Filing path always calls `SP_BUILD_FINDING` → `SP_VERIFY_FINDING` → `SP_DRAFT_FILING` — no idempotency check
2. PII gate regex (`_PII_PATTERN`) matches "national ID" even in ontology questions about hashed identifiers
3. `_REPORTING_VOCAB` safety net triggers on any question containing "filing" (even policy questions about deadlines) and the combined path escalation always builds+drafts
4. No `speculative` intent — only the regex `_UNGROUNDED_PATTERN` catches some speculation

## Implementation Steps

### Step 1: Clean up duplicate evaluation artefacts (SQL)

Keep the earliest VERIFIED finding per typology (FND-0007 for TYP-0004, FND-0008 for TYP-0001, FND-0009 for TYP-0002, FND-0010 for TYP-0003, FND-0011 for TYP-0005). Delete:

- All duplicate VERIFIED findings (FND-0012..FND-0030 except the keepers) + their claims/filings

Record before/after counts for the evidence doc.

### Step 2: Fix `app/orchestrator.py` — Idempotent Verifier path

Add a helper `find_existing_finding(cursor, typology_id)` that:
- Queries `ARGUS.GOVERNED.FINDING` for the latest finding with status IN ('VERIFIED', 'REJECTED') for that typology
- Returns `(finding_id, status, reason)` or `None`

In the filing path (`category == "file"`), before calling `SP_BUILD_FINDING`:
- Call `find_existing_finding()` for the resolved typology
- If a VERIFIED/REJECTED finding exists, **reuse it** — skip build+verify
- Log a handoff step `VERIFIER:REUSE_FINDING` with the existing finding_id

### Step 3: Fix `app/orchestrator.py` — Drafting only on explicit request

After the Verifier decision, instead of unconditionally calling `SP_DRAFT_FILING`:
- Check for existing filings via `get_filings_for_finding()`
- If filings already exist, report them without re-drafting
- Only call `SP_DRAFT_FILING` if: (a) no filings exist AND (b) the user explicitly asks to draft/prepare (detect via regex: `draft|prepare|generate.*STR|create.*report`)
- Same logic in the combined path escalation: never auto-draft

### Step 4: Fix `app/orchestrator.py` — Narrower PII gate

Change `_PII_PATTERN` to match requests **for** a person's PII value, not ontology questions about identifier types:
- Match: "what is the national ID of", "give me the phone number", "show me the name of", "who is the holder"
- Don't match: "which accounts share a national ID", "shared device or national ID across banks"

The fix: require PII-type words to be preceded by possessive/lookup phrasing (`of the|of account|behind|for customer|what is|give me|show me|reveal`) OR followed by `of the|of account|behind`.

### Step 5: Fix `app/orchestrator.py` — Narrow safety net

Change `_REPORTING_VOCAB` to only force `filing_decision` when the question references a **specific case** (contains a typology ID, finding ID, account ID, or case-referencing language like "this case/ring/network/finding").

Without a specific case reference, "filing" is treated as a policy/general question.

### Step 6: Fix `app/orchestrator.py` — Speculative intent

Add a `speculative` intent to the LLM classifier prompt. Also strengthen `_UNGROUNDED_PATTERN` to catch: "will the regulator", "what fine", "sanction", "next year", "going to be penalized", "predict", "forecast", "future audit".

The classifier can return `speculative` as an intent; if present, route to `ungrounded_refusal`.

### Step 7: Fix `sql/12_findings.sql` — Retry on grounding rejection

In `SP_DRAFT_FILING`, after the grounding check fails for an STR, retry up to 2 more times before storing `REJECTED_GROUNDING`:
- Wrap the narrative generation + grounding check in a loop (max 3 attempts)
- On each retry, append to the prompt: "PREVIOUS ATTEMPT FAILED GROUNDING: violations were [X]. Fix them."
- Same retry logic for the CONTROL_GAP_MEMO

### Step 8: Update `validation/validate_orchestrator.py`

Add new dev-set cases for the four problem classes:
- **Idempotency (I1):** Ask the same filing question twice — second call must create NO new finding and NO new filing
- **PII false-positive (PII2):** "Which accounts share a device or national ID across more than one bank?" → must NOT be refused
- **Safety-net over-trigger (SN1):** "What are the filing deadlines in the CBUAE rulebook?" → must route to policy, NOT create findings
- **Speculation (SP1):** "Will the regulator fine us for TYP-0003 next year?" → must be refused

Keep existing dev-set cases. Update report header to say "Session S10c".
